# FateQuest 引擎、内容与项目需求书

**版本：1.2 · 2026-07-30 · Godot 4.7.1 · 系统完成基线**

本文是 FateQuest 本阶段的产品、系统、数据、文本、美术、测试和交付总规格，面向产品、
程序、叙事、内容设计、美术、历史顾问与 QA。它既说明最终要达到什么，也明确当前工程
已经做到哪里，不能把“规划项”误当成“完成项”。

### 0.1 文档控制

| 项目 | 规定 |
|---|---|
| 产品负责人 | 确认范围、优先级、玩家体验与版本出口 |
| 技术负责人 | 确认状态模型、数据契约、存档迁移与性能 |
| 内容负责人 | 确认事件闭环、文本产量、effects 对齐和来源 |
| 美术负责人 | 确认资产清单、风格基线、尺寸、命名与接线 |
| QA 负责人 | 维护需求追踪表、验收用例和发布门禁 |
| 更新规则 | 范围、字段、状态机或验收口径变化时必须升小版本并写变更记录 |

### 0.2 规范用语与需求编号

- **必须**：版本出口的硬门禁，未满足不得宣称完成。
- **应**：默认实现；如不实现，负责人必须在评审记录中写明原因与替代方案。
- **可**：增强项，不阻断当前里程碑。
- 需求编号格式：`FQ-{模块}-{序号}`，例如 `FQ-SAVE-04`。测试、任务和缺陷应引用编号。

模块缩写：`CHAR` 人物、`NAR` 叙事、`DATA` 数据、`SAVE` 存档、`MAP` 地图、
`TRAVEL` 出行、`LESSON` 占卜学习、`TEXT` 文本、`ART` 美术、`QA` 验收。

### 0.3 文档权威顺序

发生冲突时按以下顺序处理：

1. 本文的产品行为、数据契约与验收口径；
2. [`ARCHITECTURE.md`](ARCHITECTURE.md) 的工程边界与依赖规则；
3. 当前 `content/tables/**/*.json` 和验证器体现的已接线字段；
4. [`STATUS.md`](STATUS.md) 的完成状态；
5. [`SYSTEM_TABLES.md`](SYSTEM_TABLES.md) 仅作早期内容概念参考，其中“双语对象直接进表”、
   `assets/data` 路径及 camelCase effect 名称均已过时，未同步前不得作为运行时规格。

字段或行为发生变化时，必须同时更新本文、验证器、样例数据和对应测试；只改文档或只改
代码都不算完成。

### 0.4 核心术语

| 术语 | 定义 |
|---|---|
| 城市情报 | 某城市的 `revealed[cityId]`，等级 0–3 |
| 道路情报 | 某路线的 `revealed[routeId]`，与城市情报相互独立 |
| 路线开放 | 已满足文书、向导、季节、物品等通行条件；不等同于“听说过路线” |
| 后果事件 | `kind: consequence` 的普通数据库事件，用于承接选择并继续给出行动 |
| 行动锚点 | 一个后果结束后，玩家明确可继续做的城市、道路、物品、线索或下一事件 |
| 学习门禁 | 小游戏成功前不执行原学习选项的任何费用、时间或习得 effect |
| 当前基线 | 已在当前 Godot 工程接线并通过自动测试的能力 |
| 发布目标 | 对外发布前必须达到，但可能仍在制作中的能力 |

## 1. 产品定义

FateQuest 是一款叠加占卜学习、占卜解读与命运分支的中世纪欧亚开放世界剧情冒险游戏。
玩家不会征服地图，而是依靠身份、语言、交谈、阅读、物品、声望与占卜，逐步理解城市
及道路，最终写成只属于本局的远行之书。

核心循环：

```text
抽取人物与起点
→ 抵达并认识城市
→ 选择探索事件
→ 立即后果 + 后续事件链
→ 获得城市/道路/物品/声望/占法
→ 在地图查看已知世界
→ 选择道路与交通方式
→ 确认出发并结算旅程
→ 抵达新城市并自动存档
```

### 1.1 体验目标

| 目标 | 玩家感受 | 可验证表现 |
|---|---|---|
| 命运给出起点，不替玩家作决定 | 抽到的是“处境”，不是强弱答案 | 三种身份均能形成可完成旅程；没有付费重抽 |
| 世界从无知变得可理解 | 地图知识来自见闻而非默认全开 | 城市与道路分别被对话、阅读和到访揭示 |
| 每次选择都留下痕迹 | 故事不会选完即断 | 选择产生反馈、状态变化和行动锚点 |
| 占卜是学习与解释 | 玩家通过操作理解方法边界 | 学习必须完成练习；解读不作现实绝断 |
| 开放世界仍有方向 | 随时可以自由探索，也知道下一步去哪 | 日志保留当前线索、未完后果与可规划路线 |

### 1.2 阶段成功指标

以下用于内部试玩和版本判断，不要求接入侵入式商业埋点：

- `FQ-PROD-01`：新玩家在 3 分钟内完成抽取并进入起点城市的比例应不低于 90%。
- `FQ-PROD-02`：主城事件可用选项的“无反馈/无状态/无锚点”比例必须为 0。
- `FQ-PROD-03`：三个身份均应能在不使用调试指令的情况下，于 30 分钟试玩中解密至少
  1 座新城市和 1 条新道路。
- `FQ-PROD-04`：玩家取消出行确认后，钱币、日期、位置、背包必须 100% 不变。
- `FQ-PROD-05`：坏档、缺少小游戏配置或无可达路线时，游戏必须回到可操作界面，不得
  黑屏、死循环或清空现有好档。
- `FQ-PROD-06`：首次导师练习的目标完成率为 50%–80%；过低说明操作说明不足，过高说明
  学习缺乏操作感。

设计红线：

- 占卜仅为游戏机制与文化叙事，不提供现实医疗、法律、财务或人生决定。
- 不使用付费抽卡、付费改运或暗改概率。
- 活态宗教的神圣场所保持敬意；不拟人化神明，不把礼仪失败做成戏谑反馈。
- 史料摘编、据史演绎与原创必须分别标记 `source / hybrid / authored`。
- 低命格打开不同内容，不生成不可玩的“废角色”。

## 2. 交付范围与完成定义

### 2.1 本轮引擎范围

| 模块 | 完成定义 |
|---|---|
| 人物抽取 | 开篇随机抽取身份；身份同步给出起点；确认后进入起点 |
| 初始知识 | 身份数据决定开局知道的 2–3 城；道路知识独立 |
| 事件分支 | `choices[] + effects[]` 驱动；支持持久化后果队列 |
| 城市探索 | 选项可产出对话后果、地图、线索、物品、声望、占法 |
| 地图 | `fatequest-worldmap` 矢量底图；已知城市可点；未知城市不可读 |
| 出行 | 选方式 → 城市简介/费用/风险 → 确认 → 动画 → 结算 |
| 存档 | 抵达自动存档；5 个手动槽；独立读取 |
| 占卜学习 | 24 法均有小游戏配置；成功才执行 `learn_divination`；可跳过 |
| 文档 | 数据表、文本、美术、里程碑、验收标准完整落档 |

### 2.2 本轮占位边界

- **正式文本暂不生产**：102 城长篇分支、24 法正式课程文案和新增 UI 本地化润色，按
  §10 的字数、语体、来源、双语和校对要求完整登记；运行时可使用现有已验收文本或带
  “（占位）”标记的短句。占位不得显示 raw key，不得承担史实或玩法教学的最终验收。
- **当前美术基线**：674 张已审计并接线的运行时资产已落盘；新流程缺图仍可使用纸面、墨线、
  色块、文字符号和现有区域回退。正式制作清单、构图、尺寸、命名和文化复核按 §11 执行。
- 占位必须可替换：文本 id、asset id、lesson method 和场景接口保持稳定，替换正式内容
  时不得修改状态机、存档结构或成败规则。
- 发布候选门禁必须输出占位清单；外部正式版本不得把未批准占位误报为完成。
- 不做战斗、联机、账号系统、云存档和付费系统。

### 2.3 平台与输入基线

- 首发基线：Windows/macOS/Linux 桌面，16:9，最低 1280×720。
- 必须支持：鼠标、键盘；所有拖拽交互必须有点击/键盘替代方案。
- 手柄与移动端是后续里程碑，数据和布局不得依赖 hover 或右键。
- UI 按 100%–200% 字号缩放验证；安全信息不能只靠颜色、声音或动画表达。
- 中文为主验收语言，英文同批进入门禁；其他语言不属于当前范围。

### 2.4 “完成”的统一定义

一项功能只有同时满足以下条件才能标为“已完成”：

1. 玩家主流程可访问，不依赖调试按钮或手工改档；
2. 数据字段、默认值、非法值和引用关系已被验证器覆盖；
3. 新增世界状态可以保存、读取和从旧版本迁移；
4. 正常、取消、失败、资源不足和读档恢复路径均有测试；
5. UI 有明确反馈、键盘焦点和最大字号检查；
6. 中英文无 raw key，文本与 effects 对齐；
7. 正式资产缺失时有不阻断流程的回退；
8. 本文“当前实现对照”与 `STATUS.md` 已同步。

状态标签统一为：

- **已实现**：满足当前工程自动测试，可进入内容生产；
- **部分实现**：核心路径可用，但发布安全、内容或表现尚缺；
- **待制作**：只有设计或数据占位；
- **阻断**：缺失会导致对应里程碑无法验收。

## 3. 人物抽取系统

### 3.1 玩家流程

1. 书案首页只提供一个主按钮“抽取人物与起点”。
2. 点击后从 `archetypes` 表抽取人物身份，卡片同步显示起点城市。
3. 卡片显示文化、信仰、旅行执念、初始语言、物品、命运修正、已知城市与已知道路。
4. 玩家总计可抽三次；每次抽取覆盖上次结果。
5. 点击“接受命运，进入〈城市〉”后才创建正式世界状态。
6. 地图、背包、事件机、时钟建立完毕，随后触发起点城市入城事件。

### 3.2 数据规则

`archetypes` 新增：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `start` | city id | 是 | 本次身份绑定的起点 |
| `knownCities` | city id[] | 是 | 含起点，共 2–3 座为宜 |
| `knownRoutes` | route id[] | 是 | 可为 0；不能由城市知识自动推断 |
| `bonus` | fate delta | 否 | 开局命运加值 |
| `malus` | fate delta | 否 | 开局命运减值 |
| `startKit` | object | 是 | 钱币、语言、物品、商品 |

运行时生成 `character`：

```json
{
  "archetype_id": "merchant",
  "background": "indian_ocean",
  "faith": "islam",
  "start_city": "ormus",
  "birth_year": 1264,
  "birth_month": 8,
  "birth_day": 17
}
```

补充约束：

- `knownCities` 必须包含 `start`，不得重复，当前推荐总数 2–3。
- `knownRoutes` 中每条路线至少应与一座 `knownCities` 城市相接，避免开局得到无法理解的
  孤立道路。
- `startKit.coins`、商品数量和物品数量不得为负；商品占用不得超过初始货格。
- 出生日期必须能转为合法 JDN；1292 年开局时角色年龄为 18–60 岁。
- `bonus/malus` 只允许修改已注册属性；最终命运值统一限制在 0–31。
- 卡片展示值来自本次候选快照，不能再次查随机数或按当前时间重新生成。

### 3.3 状态机与随机规则

```text
IDLE
→ DRAWN_1
→ DRAWN_2（可选）
→ DRAWN_3（可选，重抽禁用）
→ CONFIRMED
→ WORLD_CREATED
→ START_CITY_ENTRY
```

- `FQ-CHAR-01`：每次点击只能产生一个完整候选，身份、生日、起点和知识必须来自同一次
  随机分支。
- `FQ-CHAR-02`：同一局使用项目确定性 RNG；不得用系统随机混入状态结算。墙钟只可用于
  生成新局 seed 或存档显示时间。
- `FQ-CHAR-03`：当前三个身份等权抽取；将来如增加权重，权重必须入表、通过校验且不按
  玩家行为暗改。
- `FQ-CHAR-04`：重复抽到同一身份允许，但三次候选的生日和表现卡仍可不同；产品若改为
  “不重复身份”，须同步修改 RNG 测试。
- `FQ-CHAR-05`：确认操作必须防双击；世界只创建一次，起点入城事件只排入一次。
- `FQ-CHAR-06`：退出未确认候选不产生存档；确认后退出必须能从自动档恢复。

### 3.4 UI 与异常流程

- 抽取按钮、重抽次数、确认按钮必须处于同一视觉层级，确认按钮须写出城市名。
- 卡片至少显示：身份、起点、2–3 座已知城市、已知道路数量、语言、钱币和身份执念。
- 当前候选缺少 `start`、城市引用无效或 startKit 非法时，候选不可确认，并显示内容错误
  编号；不能悄悄回退到大不里士。
- 返回标题页时应提示“当前命运尚未确认”；已确认后返回按普通已存游戏处理。
- 200% 字号下卡片内容可滚动，确认按钮保持可见。

### 3.5 验收

- 抽取结果与进入城市永远一致，不允许卡片写“忽鲁谟斯”而状态落在“大不里士”。
- 起点地图情报为 3 级；背景城市至少 1 级。
- `knownCities` 中存在某城，不会画出未写在 `knownRoutes/revealed` 中的道路。
- 重抽未确认时不得写自动存档。
- 连续快速点击确认不会重复发放 startKit、重复推进日期或创建两个入城事件。
- 以固定 seed 跑 100 次，人物卡字段和最终世界字段逐项一致。

## 4. 城市探索与后果链

### 4.1 闭环定义

一个选项不是“按钮 + 数值变化”，必须包含以下四段：

```text
选择依据
→ 立即结算
→ 可见反馈或后果事件
→ 新行动锚点
```

新行动锚点至少一种：

- 返回当前城市并解锁一个新探索点；
- 得知一座城市；
- 得知或开放一条道路；
- 获得可在后续事件使用的物品/线索/旗标；
- 进入下一条 `consequence` 事件；
- 明确结束该支线，并把所得记录进图鉴或旅程日志。

禁止：

- 选完只关闭弹窗，无日志、无状态变化、无后续动作；
- 文本声称获得地图，effects 没有地图指令；
- effects 解锁道路，但正文和反馈不告诉玩家；
- 失败分支把玩家困在没有可用选项的事件；
- `queue_event` 指向不存在、无选择或循环触发的事件。

### 4.2 持久化后果队列

`queue_event` 把事件 id 写入 `WorldState.pending_events`。选项结算后，界面先按 FIFO
展示后果，再回城市。队列写进存档，崩溃或读档后不会丢失支线。

内部 `dequeue_event` 只由界面在打开后果页前调用，不允许内容作者手写。

推荐链长：

- 普通探索：0–1 个后果页；
- 城市支线：2–4 个事件节点；
- 主线章节：5–9 个节点，中间必须至少两次返回可自由探索状态；
- 单次连续弹窗最多 3 页，避免玩家失去开放世界控制感。

### 4.3 刺桐港示例

| 入口选择 | 立即后果 | 后果事件 | 闭环 |
|---|---|---|---|
| 向税吏报关 | +2 日、图鉴、城市情报 | 税册副本 | 得杭州与沿海道路，或拒绝并损声望 |
| 从渔阶上岸 | -2 声望、未申报旗标 | 夜巡查验 | 补费或留仓 2 日，清除未申报状态 |
| 询问船只 | +1 日、港口图鉴 | 领航人的两种说法 | 二选一得占婆海路或福州陆路 |

### 4.4 事件结算时序

`FQ-NAR-01` 至 `FQ-NAR-08` 为叙事运行硬规则：

1. `FQ-NAR-01`：打开事件时计算事件 `when`，生成可见 choice 列表；
2. `FQ-NAR-02`：每个 choice 的 `needs` 决定可用状态和锁定原因；
3. `FQ-NAR-03`：点击可用选项后立即锁定本页，防止双击；
4. `FQ-NAR-04`：如含未习得的 `learn_divination`，先进入学习门禁，原 effects 暂不执行；
5. `FQ-NAR-05`：正常 effects 严格按数组顺序执行；
6. `FQ-NAR-06`：汇总 `EffectResult`，显示结果反馈与日志；
7. `FQ-NAR-07`：当前页标记 `once_fired`，随后依 FIFO 打开 `pending_events`；
8. `FQ-NAR-08`：队列为空后返回当前城市，并刷新地图、背包、日志和可探索点。

事件打开期间不得因为 UI 重绘重新计算随机结果。带 `chance` 的 effect 使用
`eventId + effectIndex` 派生随机流，同一 seed、事件和索引必须得到同一结果。

### 4.5 失败、拒绝与循环保护

- 当前 EffectExecutor **不是事务系统**：某条 effect 被拒绝时，不回滚此前已成功的
  effect。因此资源扣除必须通过 `needs/when` 预先保证，不得把“先扣钱、后检查物品”写进
  同一分支。
- 发布目标应在内容验证器中模拟明显的负库存、负钱币和空事件队列风险；高价值复合交易
  应由专用核心服务一次验证后结算。
- `queue_event` 目标必须存在、必须至少有一个选择，并且不能直接或无条件间接回到自身。
- 同一结算连续打开后果页最多 3 个；超过时暂停队列，回到城市并在日志提供“继续处理”
  入口。
- 读档发现队首事件不存在时：记录错误、将该 id 移入 `extra.recovery.skipped_events`、
  继续下一项，不得永久卡住存档。
- 后果页中所有选项都被锁定时，必须存在一个无条件退出选项，或由引擎提供“暂时离开”
  回城市。

### 4.6 线索与任务可读性

- 旅程日志须显示“刚刚发生”“得到的线索”“可继续行动”三类信息。
- 城市或道路被揭示时，反馈文本必须给出名称；不允许只出现“地图已更新”。
- 支线明确结束时写完成句，不保留看似可继续但没有数据库节点的悬空目标。
- 旗标命名采用 `fl-{city|arc}-{slug}`；内容看板记录谁设置、谁读取、谁清除。
- 关键线索不得只有一个不可逆获取点；主线至少准备另一个 NPC、阅读物或到访触发的补救
  来源。

### 4.7 内容闭环验收表

每个选项提交 QA 前逐项回答：

| 检查项 | 通过条件 |
|---|---|
| 为什么能选 | 正文提供了足够信息；锁定时能解释缺少什么 |
| 立即发生什么 | 有 resultText、后果页或明确状态反馈 |
| 数据改变什么 | effects 与正文逐项对齐，无无理由指令 |
| 下一步是什么 | 至少一个行动锚点，或明确写支线结束 |
| 能否恢复 | 失败、资源不足、退出和读档后仍可操作 |
| 会不会重复 | once、旗标和队列规则防止重复领取 |
| 是否有死路 | 主线线索有补救路径，所有后果页有可用出口 |

## 5. 数据库与表结构

### 5.1 通用规范

- JSON 是唯一运行时内容真相源，不在 GDScript 写城市 id 分支。
- id 为小写 ASCII 与连字符，全局唯一，发布后永不复用。
- 玩家可见文本只存 i18n key；中文和英文在 `content/i18n` 编译产物中。
- 所有 effect 必须有 `reason`，用于日志、音效、QA 与 bug 报告。
- 所有引用在内容门禁中校验存在性。
- JSON 数字进入 Godot 后统一归一化；钱币使用整数 fen，不使用浮点货币。

每个表文件必须采用统一包络：

```json
{
  "contentVersion": 1,
  "table": "events",
  "records": []
}
```

约束：

- `contentVersion` 是内容结构版本，不等于存档 `version`；结构变化必须提供构建迁移脚本。
- 同一逻辑表可按区域拆成多个文件，但 `table` 必须相同，所有 `records[].id` 仍全局唯一。
- 运行时只读 `content/tables`；`content/story` 是文本创作源，经 `story.mjs build` 编译到
  `content/i18n`，不得只修改编译产物。
- 数组默认保持作者顺序；需要随机的池必须在字段定义中明确，并使用确定性 RNG。
- 枚举新增值须先更新验证器和回退表现；未知枚举不得静默当默认值。
- 经度范围 `[-180,180]`、纬度范围 `[-90,90]`；月份使用 1–12；风险使用整数 0–5。
- 文本 key 必须在中文和英文存在；`I18n.t(key) == key` 视为发布阻断。

### 5.2 城市表 `cities`

| 字段 | 类型 | 必填 | 用途 |
|---|---|---:|---|
| `id` | string | 是 | 城市唯一 id |
| `name` | text key | 是 | 城市名 |
| `band` | enum | 是 | 经济与区域分组 |
| `culture` | enum | 是 | UI、美术、礼仪与历法 |
| `faiths` | id[] | 是 | 当地常见信仰 |
| `coord` | `[lon,lat]` | 是 | 与 worldmap 对齐 |
| `tier` | enum | 是 | metropolis/city/town/station |
| `entryEvent` | event id | 是 | 抵达时触发 |
| `sites` | event id[] | 按 tier | 城市探索点 |
| `mentor` | npc id | 否 | 地方导师引用；学习入口仍由城市事件或导师事件提供 |
| `market` | object | 按 tier | 商品、货币、价差 |
| `exits` | route id[] | 是 | 图数据引用，不代表玩家已知 |
| `lore` | object | 是 | 来源、书目与处置说明 |
| `intro` | text key | 建议 | 地图详情卡的短简介；缺失时回退入城正文 |

### 5.3 路线表 `routes`

| 字段 | 类型 | 必填 | 用途 |
|---|---|---:|---|
| `id` | route id | 是 | `rt-{from}-{to}` |
| `from/to` | city id | 是 | 两端城市 |
| `reverse` | bool | 是 | 是否可逆 |
| `kind` | enum | 是 | land/sea/river/coastal，限制交通类别与表现 |
| `modes` | transport id[] | 是 | 可选交通方式 |
| `days/cost/risk` | int | 是 | 基础时长、费用与风险 |
| `distanceKm` | int | 是 | 旅程记录和结局 |
| `season.open` | month[] | 否 | 开放月份 |
| `hazards` | id[] | 否 | 货损与事件上下文 |
| `encounters` | event id[] | 否 | 途中事件池 |
| `trunk` | bool | 否 | 主干路线绘制 |
| `unlock` | Condition | 发布目标 | 文书、向导、身份等路线开放条件；组合使用 any/all/not |

路线概念必须分三层：

- **知道城市**：`revealed[cityId] > 0`，只说明知道目的地存在；
- **知道道路**：`revealed[routeId] > 0`，地图可显示并可查看规划信息；
- **现在可通行**：方向、季节、交通方式、钱币、物品及 `unlock` 条件全部满足。

当前基线中的 `unlocked_routes` 是兼容旧内容的“已开放并至少揭示一级”列表，Travel 暂未把
`route.unlock` 作为独立许可门禁。正式内容开始使用“知道但尚无许可”的路线之前，
`FQ-TRAVEL-09` 必须补齐统一路线条件 evaluator；在此之前不得写正文声称“路线可见但需
许可”却允许直接出发。

路线方向要求：

- `reverse: false` 时只允许 `from → to`；
- `reverse: true` 时两向均可，但季节、费用或 encounters 如需方向差异，应拆成两条记录；
- 城市 `exits` 必须包含所有从该城可发起的路线引用，且与路线方向一致。

### 5.4 事件表 `events`

| 字段 | 类型 | 必填 | 用途 |
|---|---|---:|---|
| `id` | event id | 是 | 唯一 id |
| `kind` | enum | 是 | entry/site/road/consequence 等 |
| `title/body` | text key | 是 | 标题与正文 |
| `when` | Condition | 否 | 事件级出现条件 |
| `scene` | object | 否 | 背景、NPC、美术回退 |
| `choices` | Choice[] | 是 | 分支入口 |
| `once` | bool | 是 | 是否只结算一次 |
| `priority` | int | 否 | 候选优先级 |
| `lore` | object | 是 | 来源标记 |

当前基础 kind：`entry` 入城、`site` 城内探索、`road` 途中、`consequence` 选择后果。
`court`、`retainer`、`festival`、`crisis` 可在对应调度器完成后加入；新增 kind 前必须定义
触发来源、once 规则、候选优先级和无候选回退。

### 5.5 选项结构 `Choice`

| 字段 | 类型 | 必填 | 用途 |
|---|---|---:|---|
| `label` | text key | 是 | 玩家看到的行动句 |
| `needs` | Condition | 否 | 钱、语言、身份、物品、声望等 |
| `effects` | Effect[] | 是 | 按数组顺序执行 |
| `divination` | method id | 否 | 调占卜引擎 |
| `pass/fail.effects` | Effect[] | 占卜选项 | 成败叙事附加效果 |
| `pass/fail.text` | text key | 占卜选项 | 成败结果正文 |
| `showWhen` | Condition | 否 | 不满足时隐藏；不改变原始选项索引 |
| `resultText` | text key | 否 | 无后果页时的即时可读反馈 |
| `lessonFailEffects` | Effect[] | 否 | 练习失败并离开时执行；跳过不执行 |

`needs` 与事件 `when` 使用同一 Condition 语法，但语义不同：`when` 不满足时事件不出现；
`needs` 不满足时选项仍应可见并禁用，以便玩家知道缺少什么。涉及剧情保密的隐藏选项应
使用单独的 `showWhen` 字段，不得滥用 `needs`。核心结算会再次检查该条件，不能通过
直接调用隐藏选项索引绕过。

### 5.6 结果与后果

结果不另建硬编码类。一次结果由三部分组成：

```text
EffectResult
  applied[] / rejected[] / log_lines[]
  queued_days / queued_events[]
  reading（若调用占卜）
```

如需长文本、二次选择或 NPC 追问，使用 `queue_event` 指向
`kind: "consequence"` 的普通事件记录。

最小闭环样例：

```json
{
  "id": "ev-city-rumour",
  "kind": "site",
  "title": "ev.city.rumour.title",
  "body": "ev.city.rumour.body",
  "once": true,
  "choices": [
    {
      "label": "ev.city.rumour.choice.ask",
      "needs": { "language": "persian" },
      "effects": [
        {
          "op": "reveal_city",
          "value": "ormus",
          "level": 1,
          "reason": "the-sailor-named-ormus"
        },
        {
          "op": "queue_event",
          "value": "ev-city-rumour-consequence",
          "reason": "the-sailor-drew-the-road"
        }
      ]
    }
  ],
  "lore": { "origin": "authored" }
}
```

### 5.7 Condition 指令

支持 `any/all/not` 组合，以及：

`cities`、`bands`、`faiths`、`season`、`years`、`flags`、`not_flags`、
`has_item`、`lacks_item`、`learned_divination`、`language`、`min_reputation`、
`fate`、`coins`、`etiquette`、`has_retainer`。

未知字段必须失败，不做静默忽略。

Condition 语义：

- 同一对象中的叶字段为 AND；
- 单个叶字段的数组值按该字段定义解释，例如 `cities` 为命中任一城市，
  `has_item` 为必须拥有数组中的全部物品；
- `any: Condition[]` 至少一项为真，`all: Condition[]` 全部为真，`not: Condition`
  结果取反；
- 空或 null 条件为 true；
- `has_retainer` 支持 `{id}` 或 `{role}`；只计算 `present != false` 的在场成员，职业从
  `retainers.roles/role/job` 数据读取。

### 5.8 Effect 指令

| op | 必要参数 | 效果 |
|---|---|---|
| `coins` | `value` | 钱币增减；不得欠款 |
| `days` | `value` | 推进天数和 JDN |
| `goods` | `id,value` | 商品增减 |
| `item/remove_item` | `value` | 获得/移除剧情物品 |
| `cargo_slots` | `value` | 货格增减 |
| `reputation` | `scope,id,value` | 城市或区域声望 |
| `faith/language/etiquette` | 对应参数 | 身份知识变化 |
| `fate` | `id,value` | 三条命运修正，限制 0–31 |
| `reveal_map` | `value` | 兼容旧内容，情报 +1 |
| `reveal_city` | `value,level` | 设置城市最低情报等级 |
| `reveal_route` | `value,level` | 设置道路最低情报等级 |
| `unlock_route` | `value` | 加入兼容开放列表并至少揭示 1 级；独立许可目标见 §5.3 |
| `learn_divination` | `value` | 习得占法；玩家界面必须先通过练习 |
| `flag/unflag` | `value` | 设置/清除剧情条件 |
| `queue_event` | `value` | 排入持久化后果链 |
| `goto` | `value` | 抵达城市并记录旅程 |
| `recruit/dismiss` | `value` | 随从加入/离开 |
| `retainer_mood/reveal_birth` | `id,value` | 随从关系与秘密 |
| `sticker/codex` | `value` | 图鉴与结局收集 |

`dequeue_event`、`active_event`、`fire_event`、`journey`、`end_journey`、`recovery`、
`leg`、`bought`、`trade` 为引擎内部指令，内容作者通常不手写。

所有 Effect 的公共字段：

| 字段 | 类型 | 规则 |
|---|---|---|
| `op` | string | 必须是注册指令 |
| `value` | Variant | 按 op 定义；不得依赖字符串隐式转数字 |
| `id/scope/level` | Variant | 按 op 需要提供 |
| `reason` | string | 必填、ASCII slug，用于日志与问题定位，不直接展示给玩家 |
| `chance` | float | 可选，范围 0–1；省略为 1 |

执行规则：

- effects 严格按数组顺序执行，不排序、不批处理；
- chance 未命中或资源非法进入 `rejected[]`，后续 effect 仍继续；
- 内容作者必须避免让后续指令依赖一个可能被拒绝的前序指令；
- 玩家反馈由 `EffectResult` 汇总，不能把内部 `reason` 原样显示为正式文案；
- `preview()` 必须在世界状态深拷贝上执行，与正式结算共用同一路径。

### 5.9 数据变更流程

1. 在创作源或表文件中修改；
2. 更新 schema/验证器；
3. 如改文本，执行 `story.mjs build → stamp zh → check`；
4. 运行 `validate.mjs`；
5. 运行受影响的 Godot 单测和流程烟测；
6. 更新存档迁移与版本；
7. 更新本文样例和 `STATUS.md`。

禁止只在 `content/i18n/*.json` 修文案；下一次构建会被 `content/story` 覆盖。禁止在没有
迁移的情况下删除、改义或复用已发布 id。

## 6. 存档管理

### 6.1 存档点

- 自动槽 `auto`：抵达城市后，在入城选择之前写入。
- 手动槽：`manual-1` 至 `manual-5`，允许覆盖。
- 后续正式版增加：离城前、重大后果链完成后、占卜结算后轮换自动档。

写档时序：

```text
旅程逻辑结算完成
→ state/clock 一致性检查
→ 写临时文件
→ 校验临时文件可读
→ 备份旧槽
→ 替换正式槽
→ 更新存档界面
```

手动覆盖必须二次确认，确认框显示目标槽的城市、局内日期和现实保存时间。自动槽不可在
界面手动覆盖，可读取；删除存档属于设置中的独立操作，不与“新游戏”绑定。

### 6.2 必存数据

| 类别 | 字段 |
|---|---|
| 角色 | `character`、archetype、出生日期、信仰、语言、命运 |
| 位置时间 | 当前城市、JDN、已过天数、起点、到访顺序 |
| 地图 | 城市/路线情报等级、已开放道路 |
| 背包 | 钱、剧情物品、商品、货格、成本基础 |
| 社会 | 城市声望、区域声望、礼仪、旗标 |
| 随从 | 名单、加入日、情谊、在场状态、生辰封印 |
| 图鉴 | codex、stickers |
| 剧情 | once_fired、pending_events |
| 旅程 | 最长路段、最佳贸易 |

### 6.3 技术要求

- 快照为权威，不以 effect 回放重建世界。
- 临时文件写完再原子替换，避免断电产生半份存档。
- `saveVersion` 只允许逐版本单向迁移。
- v1 → v2 为旧档补 `character` 与 `pending_events` 空值。
- 读取菜单只读 header，不反序列化完整世界。

发布安全要求：

- `FQ-SAVE-01`：每个槽保留上一份 `.bak`；新临时文件通过 JSON、版本和必填字段校验后
  才能替换旧档。
- `FQ-SAVE-02`：header 至少包含槽位、城市、局内日期、已过天数、钱币、人物身份、
  保存时间、版本和缩略图 id。
- `FQ-SAVE-03`：加入内容摘要或 checksum，区分损坏与普通缺档；不把校验失败文件覆盖掉。
- `FQ-SAVE-04`：读取失败时提供“尝试备份”“返回”“查看错误编号”，不得自动开新局。
- `FQ-SAVE-05`：迁移在内存副本上完成，成功反序列化后才允许另存为新版本。
- `FQ-SAVE-06`：比当前游戏更高版本的存档只读显示“不兼容”，不得由旧版重写。
- `FQ-SAVE-07`：任何写档失败只影响本次保存；保留原槽并在 HUD 显示可关闭提示。
- `FQ-SAVE-08`：同一槽快速连续点击只能有一个写任务。

当前实现为存档 v3：临时文件写入后执行结构、版本和 SHA-256 回读验证；安装新文件前
保留上一份 `.bak`，失败时恢复；`.fqhead` sidecar 供列表仅读 header 与文件长度。损坏
正式档拒绝反序列化，界面显示错误编号并允许恢复已验证备份；v1/v2 仍按单向链迁移，
更高版本只显示不兼容。该路径由截断档、checksum、路径穿越、备份恢复和字段全覆盖测试
验证。

### 6.4 槽位显示与恢复验收

- 空槽显示“空”，不得残留上一局城市。
- 已有槽显示本地化城市名、人物身份、第几日、局内日期和现实保存时间。
- 自动槽保存失败后，玩家仍停留在已抵达城市，可继续或再次保存。
- 五个手动槽交叉读取后，角色、位置、地图、背包、声望、随从、图鉴、天数和后果队列
  均与各自快照一致。
- 依次测试：截断 JSON、未知 version、缺 header、缺 state、队首事件丢失、城市 id 丢失。
- 迁移测试必须保存固定 v1 fixture，不可用当前 serializer 临时伪造旧档。

## 7. 地图系统

### 7.1 为什么此前看起来像贴图

此前 Godot 地图虽已用 `Node2D` 绘制城市、道路、山脉和迷雾，但羊皮纸与装饰贴图占据
视觉主体，`fatequest-worldmap` 的海岸线、河流和海域标注没有进入导出包；因此玩家看到
的更像一张不能表达真实地理关系的插画。原因是 `worldmap/` 带 `.gdignore`，直接运行时
读取会在编辑器可用、导出后丢失。

正确方案：

```text
fatequest-worldmap/*.geojson
→ sync_world_config.mjs 过滤/抽稀
→ content/world/vector_map.json
→ Godot WorldMap 投影绘制
```

贴图只负责材质和装饰，矢量数据负责海岸、河流、海域、城市、道路和点击命中。

### 7.2 交互规则

- `FQ-MAP-01`：运行时地理关系来自打包后的 worldmap 矢量产物，装饰贴图不得承担点击数据。
- `FQ-MAP-02`：0 级城市没有名称、语义图标和命中区，揭示后才成为可交互城市。
- `FQ-MAP-03`：城市与道路各自使用 0–3 级情报，不相互推导。
- `FQ-MAP-04`：已知城市可打开详情卡；卡片只显示该情报等级允许的信息。
- `FQ-MAP-05`：地图更新必须来自 effect 或到访结算，不根据正文关键词自动猜测。
- `FQ-MAP-06`：缩放、平移、命中、键盘焦点和遮罩在 1×–6× 下保持一致。

- 未知城市：不显示名称、等级和命中区；最多是与普通纸面污点无法区分的不可读墨点。
- 1 级“听说过”：可点，显示名字、方位、有限简介；道路独立。
- 2 级“有描述”：显示完整简介与主要已知道路。
- 3 级“到访/详知”：显示完整卡、城内状态、市场等后续扩展信息。
- 当前城市始终按 3 级显示。
- 点击已知城市弹详情卡：简介、情报等级、已知道路、每条路的交通方式。
- 缩放 1–6 倍，鼠标滚轮与按钮均可操作；拖动平移；“归位”回当前城。
- 新情报通过 shader 迷雾溶解；新走过路线逐段描画。

情报显示矩阵：

| 情报 | 城市图标 | 名称 | 简介 | 市场/探索 | 道路 |
|---:|---|---|---|---|---|
| 0 未知 | 无语义污点 | 否 | 否 | 否 | 否 |
| 1 听闻 | 简化轮廓 | 是 | 方向与一句话 | 否 | 只列已知道路 |
| 2 描述 | 完整小像 | 是 | 完整已知简介 | 可提示特色 | 只列已知道路 |
| 3 到访/详知 | 完整并带印章 | 是 | 完整 | 显示已发现状态 | 只列已知道路 |

路线自己的 1/2/3 级分别表示：听闻走法、掌握季节与风险、亲自走过或获得详图。路线显示
等级不得使用两个端点城市等级的最小值替代。

### 7.3 图层与命中

从底到顶的固定图层：

```text
羊皮纸材质
→ 海陆底色
→ 海岸/河流/海域矢量
→ 山脉与装饰
→ 已知道路
→ 已知城市
→ 标签
→ 情报迷雾
→ 旅行动画
→ 详情卡与操作 UI
```

- 矢量坐标在 `setup()` 时投影并缓存，`_draw()` 不重新解析 JSON。
- 点击命中使用地图局部坐标，必须反算 zoom/pan；命中半径在屏幕空间保持 20–28 px，
  不随缩放变得不可点。
- 重叠城市先按距离，再按当前城市、更高情报和更高 tier 决定；完全同级时按稳定城市 id 决定，玩家可放大后重选。
- 拖动阈值超过 6 px 后不得误触城市；详情卡打开时地图停止接收点击。
- 键盘模式用方向键在当前可见已知城市间移动焦点，Enter 打开，Esc 关闭。
- 海岸、河流、海域名称属于底图知识，不应意外泄露未知城市；政治边界不属于当前范围。

### 7.4 知识与可达性

- `knownCities` 不推导 `knownRoutes`。
- NPC 正文说出地名时，至少配 `reveal_city`。
- NPC 明确描述走法、航线、驿路或地图时，配 `reveal_route`。
- 需要文书/向导/许可的路线，在得知后仍用 `unlock_route` 或物品条件控制。
- 地图不列出未知路，出行核心也拒绝绕过 UI 调用未知路。

核心 Travel 已分别检查道路知识和 `route.unlock`，UI 与直接核心调用共用同一 evaluator；
知道城市、知道道路和获得通行许可三者均不会相互隐式推导。

### 7.5 城市详情卡

详情卡必须包含：

- 本地化城市名、文化圈、城市等级和情报印章；
- 根据情报裁剪的 80–180 字简介；
- 当前是否到访、与当前位置的关系；
- 已知道路列表：目的地、方向、开放月份、已知风险；
- 每条路所有交通方式及禁用原因；
- “规划出行”与“关闭”操作。

不允许：

- 因知道城市而自动补出道路；
- 对 1 级情报显示完整价格表；
- 详情卡打开后点击穿透到另一座城市；
- 用 raw id 代替缺失城市名。

### 7.6 worldmap 数据验收

- `sync_world_config.mjs` 输出必须可重复；相同输入产生字节级稳定或语义级稳定结果。
- 构建记录输入文件、抽稀参数、点数和输出大小。
- 海岸线不自相交到影响大陆辨认，主要河流在 1× 与 6× 都不压过路线。
- worldmap 源目录即使被 `.gdignore` 排除，导出包仍必须包含运行时 `vector_map.json`。
- 桌面导出包离线启动，不依赖开发仓库相邻目录。

## 8. 出行

完整状态机：

```text
城市“上路”
→ 只列当前城市的已知道路
→ 展示该路全部可用交通方式
→ 选择方式
→ 目的城市简介卡（方式/天数/费用/风险）
→ “确定出发”
→ 扣费、工资、货损、日期、位置结算
→ 路线描画 + 旅行动画
→ 途中事件
→ 抵达、自动存档、入城事件
```

要求：

- 选择方式不改变世界状态，确认出发才改变。
- 禁用项在按钮正文写出原因，不只放 tooltip。
- 模式影响时长、费用、风险、物品要求和随从货格。
- 动画不得阻塞逻辑或决定结算结果；“减少动态效果”下改为淡入淡出。
- 中途事件在目的城市入城事件之前处理。

### 8.1 可用性计算

交通方式按钮必须使用核心 Travel 的统一结果，不在 UI 复制规则。检查顺序：

1. 路线是否已知；
2. 当前城市是否符合路线方向；
3. 月份是否在 `season.open`；
4. mode 是否属于路线且 `transport.kinds` 与 route.kind 兼容；
5. 钱币是否覆盖路线费用 + 交通雇佣费用；
6. mode 所需物品是否拥有；
7. 路线许可、当前货物与该交通方式/道路适用的随从货格。

禁用原因可同时显示多项；费用统一以最小货币单位存储、格式化后展示。预计天数至少为
1 日，风险最终限制 0–5。

### 8.2 确认与结算边界

- `FQ-TRAVEL-01`：确认卡是纯预览，关闭、Esc、切换方式均不执行 effects。
- `FQ-TRAVEL-02`：点击确定后再次调用 availability，防止界面停留期间状态变化。
- `FQ-TRAVEL-03`：确定按钮立即禁用，避免重复扣费和推进日期。
- `FQ-TRAVEL-04`：基础结算顺序固定为扣费 → 推进日期 → 移动位置 → 揭示目的地/道路 →
  记录最长路段。
- `FQ-TRAVEL-05`：出发失败时保持原城市和日期；如已发生部分结算，视为 P0 缺陷。
- `FQ-TRAVEL-06`：旅行动画只播放已结算的结果，跳过动画不得改变 encounter RNG。
- `FQ-TRAVEL-07`：抵达后先落自动档，再打开入城事件；途中未完后果须在入城前恢复。
- `FQ-TRAVEL-08`：单向路线反向不可出现在上路列表。
- `FQ-TRAVEL-09`：统一评估路线许可条件，区分“已知”与“可通行”。

### 8.3 途中事件与风险

正式旅途根据风险、hazards、season bonus、mode 和随从产生 0–2 个途中事件。要求：

- 事件抽取使用 `travel:{routeId}:{departureJdn}:{index}` 派生随机流；
- 同一旅程不会重复同一个 `once` 事件；
- 途中事件可改变日期、货物、声望或随从，但不得直接打开未知道路；
- 玩家在途中事件退出后，读档应恢复到事件前安全点或明确的旅途快照；
- 无 encounter 数据时按基础结果抵达，不能阻断。

当前 Travel 已完成方向、道路知识、季节、mode、交通类型、钱币、物品、`route.unlock`
和货格检查；确认时二次校验，失败不改变状态。合法旅程按派生随机流抽取 0–2 个适用道路
事件，跳过已触发 once 事件，持久化 `active_journey + pending_events + active_event`。
途中自动档读回后先恢复 FIFO 道路事件，事件耗尽才结束旅程、抵达存档并打开入城事件。
工资与货损在同一确认流程中结算且不影响遭遇随机流。

### 8.4 出行动画规格

- 路线墨线：0.45–1.4 秒，按天数轻微缩放并封顶；
- 交通循环：2–4 秒素材，界面实际展示不强制等完整循环；
- 结算摘要在动画期间可读，包含出发城、目的城、方式、天数、费用和发生的途中事件数；
- Esc/点击跳过只结束表现，不跳过结算和事件；
- 减少动态效果模式：无平移、摇摆和快速缩放，仅 150–250 ms 淡入淡出。

## 9. 占卜学习小游戏

### 9.1 学习门禁

导师事件中的选项仍由数据库给出费用、天数和学习 effect。玩家点击学习时，表现层先查
`lesson-{method}`，启动练习；只有 `passed` 后才继续执行原选项，因此费用、天数、旗标
和 `learn_divination` 一起结算。`failed/skipped` 不执行学习选项。

### 9.2 六类练习引擎

| type | 操作 | 检验能力 | 当前占位表现 |
|---|---|---|---|
| `throw` | 完成规定投掷，再选择记录/解读 | 工具操作与记录边界 | 确定性象位数字与按钮 |
| `arrange` | 从乱序项按正确次序排列 | 结构记忆 | 乱序按钮 |
| `observe` | 主动记录线索，再选择有限度解读 | 观察与伦理边界 | 观察/回答按钮 |
| `timing` | 游标进入时窗时定象 | 节律与时机 | 进度条；辅助后无计时 |
| `deduce` | 组合筹片精确达到目标 | 数理推演 | 数值筹片与重置 |
| `form` | 逐步生成盘、宫或符号结构 | 成象过程 | 分步按钮 |

24 个方法均有合法配置，六类均至少一课。纯逻辑 `LessonEngine` 决定成败、尝试和辅助；
UI 与未来正式美术不拥有规则。投掷使用命名随机流，同种子结果一致。

`divination_lessons` 字段契约：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | string | 是 | 固定为 `lesson-{method}` |
| `method` | divination id | 是 | 一法恰好一课 |
| `type` | enum | 是 | throw/arrange/observe/timing/deduce/form |
| `title` | text key | 是 | 课程标题 |
| `prompt` | text key | 是 | 操作目标与方法边界 |
| `steps` | text key[] | arrange/form | 正确顺序，至少 3 项 |
| `clues` | text key[] | observe | 可主动记录的观察 |
| `options` | text key[] | observe/throw | 2–4 项，错误项不能传播有害绝断 |
| `answer` | int | observe/throw | 合法索引 |
| `throws/faces` | int/int | throw | 至少投掷 1 次；面数至少 2 |
| `window` | `[0,1]` | timing | 起点 < 终点，推荐宽度 0.12–0.25 |
| `values/target` | int[]/int | deduce | 至少存在一种可达目标组合 |
| `difficulty` | object | 正式内容 | 容错、速度、提示次数，不改变文化知识 |
| `assist` | object | 正式内容 | 美术演示与教学文案；逻辑辅助已接线 |

T1（2026-08-06）已把 24 课 `title/prompt/steps/clues/options` 全部迁移为 `lesson.*` i18n key，
中英文本落库并逐项完成文化校读（G7/G18/G24/G21 通过）。`placeholderText` 字段已移除。
替换未改变 method、type 或 pass/fail 数据契约。

### 9.3 量产美术后的特色升级

正式版在同一数据接口下扩为六个视觉适配器：

- 投掷：铜钱、筊杯、卢恩、星骰使用物理落定；
- 排列：塔罗、雷诺曼、神谕拖拽布阵；
- 观测：梦、水晶、咖啡、面相、手相做局部观察与标记；
- 计时：签筒、奇门、梅花、风水做节律/定向；
- 推演：八字、紫微、西占、吠陀在盘面安置要素；
- 成象：易、六爻、沙盘按步骤生成最终符号。

难度只影响操作窗口和容错，不用现实玄学知识卡住玩家。连续失败两次后应提供
“导师慢速演示”，但仍需玩家完成最后一步。

### 9.4 尝试、失败与跳过

- `FQ-LESSON-01`：第一次打开先显示目标和操作，不在说明消失前开始计时。
- `FQ-LESSON-02`：成功后才执行原 choice，包括费用、天数、旗标和习得；这些必须只执行
  一次。
- `FQ-LESSON-03`：失败不习得，不执行原 choice；导师给出具体错误反馈和“重试/暂时离开”。
- `FQ-LESSON-04`：跳过不扣费、不推进日期、不降声望，并返回导师或城市。
- `FQ-LESSON-05`：连续失败次数属于当前导师会话，不写成永久惩罚；第二次失败后出现辅助。
- `FQ-LESSON-06`：已经习得的方法再次选择“学习”时改为复习/施占，不重复扣学习费。
- `FQ-LESSON-07`：课程缺失或字段非法时禁用学习选项并给内容错误编号，绝不能直接发技能。
- `FQ-LESSON-08`：关闭窗口等同“暂时离开”，不得遗留半个 lesson pending 状态。

### 9.5 无障碍与公平性

- timing 必须提供“放慢 50%”和无计时替代；不把反应速度作为习得唯一门槛。
- order 选择后要有已选序列文字，不只靠位置或颜色。
- balance 提供撤回或重置；正式版不得要求玩家故意溢出后重开整个导师事件。
- interpret 支持屏幕阅读顺序，正确答案不能只靠晦涩现实知识。
- 所有小游戏可用键盘完成，焦点轮廓清晰；音效仅作增强。
- 成功、失败、跳过三种结果都返回稳定 UI，且在日志留下可理解记录。

## 10. 文本需求

### 10.1 写作原则

- 叙述视角：第二人称现在时，像旅行者正在记录见闻。
- 语体：清楚可读的现代中文为骨架，适量使用当时地名、货币、官职和旅行见闻语汇。
- **文言文现代化登记（2026-08-02）**：12 主城入城长文已完成文言→现代汉语改写；其余城市与事件中仍存在的行纪文言（"乃/之/盖/亦"等）按同规则现代化，作为后续内容批次任务，不允许回归为不可读的文言行文。
- 不伪造史料原句；神话和夸张可存在，但必须标 `hybrid/authored`。
- 选项使用动词开头，写“做什么”，不提前泄露概率结果。
- 失败写成代价或误读，不羞辱玩家，不把文化差异写成文明高低。
- 占卜结果给风险、倾向和备选行动，不给绝对命令。

### 10.2 各模块文案清单

| 模块 | 每单元文本 | 建议长度 |
|---|---|---:|
| 人物卡 | 身份名、执念、背景简介、起点缘由 | 80–140 中文字 |
| 城市地图卡 | 一句话定位 + 已知简介 | 80–180 字 |
| 入城事件 | 感官入口、当地秩序、当前阻碍 | 300–500 字 |
| 探索事件 | 场所描写、人物诉求、可行动信息 | 220–420 字 |
| 途中事件 | 路况/天气/同伴/风险 | 160–300 字 |
| 后果事件 | 明确承接上个选择，陈述新局面 | 120–260 字 |
| 选项 | 动词行动句 | 8–24 字 |
| 即时反馈 | 做了什么、失去/获得什么 | 30–90 字 |
| 物品/线索 | 名称、来源、后续用途暗示 | 40–100 字 |
| 道路情报 | 两端、走法、季节、风险来源 | 60–140 字 |
| 占法导师 | 方法边界、文化语境、学习代价 | 220–380 字 |
| 小游戏提示 | 目标、操作、失败含义 | 30–80 字 |
| 图鉴 | 定义、地方观察、来源 | 120–260 字 |
| 出行确认 | 目的地简介、方式、天数、费用、风险 | 80–180 字 |
| 存档 | 槽位、城市、第几日、保存时间 | 单行 |

### 10.3 十二主城文本产量基线

每座主城至少包含：

| 内容 | 数量/城 | 分支要求 |
|---|---:|---|
| 城市地图简介 | 1 | 情报 1 级短版、2–3 级长版 |
| 入城事件 | 1 | 3 个选项，至少 2 个有后果页 |
| 探索点事件 | 3 | 每个 2–4 选项，至少一个信息锚点 |
| 导师/占法事件 | 1 | 学、问而不学、暂时离开 |
| 后果事件 | 3–6 | 承接具体选项，不使用通用万能结果 |
| 道路情报 | 2–4 | 城市存在与道路走法分开写 |
| 独特物品/图鉴 | 2–4 | 写来源和后续用途暗示 |
| 即时反馈 | 每个无后果页选项 1 | 与 effects 对齐 |

按 12 城估算，C1 需要复核约 96–132 个事件节点、36–48 条道路情报和 24–48 条物品/
图鉴文本。中文正文建议控制在约 3–4 万字，再制作英文对应文本；已有可复用史料文本仍需
按新后果链重新校对，不因“已有事件数”自动视为完成。

### 10.4 后果链写作模板

```markdown
标题：必须能看出这是上一选择的后果
承接句：重复一个可辨识动作/人物/物件，禁止无缘由跳场
局面句：说明现在发生了什么
信息句：给玩家判断下一步所需信息
选项 A：承担较明确的资源代价，换确定结果
选项 B：承担时间/声望/关系代价，换另一结果
effects：逐句对齐正文中出现的获得与损失
结束：落到城市、道路、物品、旗标或下一事件
```

### 10.5 文本创作与校对流程

```text
史料卡/原创提案
→ 事件结构和行动锚点
→ 中文初稿
→ effects 对齐
→ 历史/宗教校读
→ 英文改写
→ i18n 构建与时效检查
→ UI 实机排版
→ QA 分支通读
```

职责分离：

- 叙事负责语气、人物动机、承接和可读性；
- 内容设计负责 needs/effects、状态、线索补救与闭环；
- 历史顾问检查年代、地名、物质文化、宗教和史料处置；
- 本地化不是逐字翻译，应保留信息、选择意图和礼貌程度；
- QA 按真实主流程逐个选项验证，不只在 JSON 中读文本。

单条事件校对清单：

1. 时间、地理、交通耗时和季节是否自洽；
2. 人物是否知道其身份能够知道的信息；
3. 首句是否承接来源场景，代词指向是否清楚；
4. 每个选择是否表达行动而非作者评价；
5. 获得/损失的名词、数量、天数和声望是否与 effects 一致；
6. 城市情报与道路情报是否被错误混写；
7. 失败是否仍给信息、代价或补救，而非简单“你失败了”；
8. 是否无意绝对化占卜、污名化族群或把礼仪写成奇观；
9. 中英是否信息等价，UI 长度是否可容纳；
10. source/hybrid/authored 和书目是否正确。

### 10.6 i18n 与敏感性

- key 规范：`ev.{city}.{slug}.{field}`、`city.{id}.intro`、
  `lesson.{method}.{field}`。
- 中英必须同批提交；缺译时回退英文并标注，不显示 raw key。
- 宗教、族群、残障、性别与殖民语汇在上线前做敏感读者审阅。
- 外来语第一次出现时给括注，不让理解任务依赖未解释术语。
- UI 在最大字号下不得靠截断文本解决溢出。

文本源管理：

- 城市与事件长文本优先维护在 `content/story/<unit>/{en,zh}.md`；
- Markdown frontmatter 中记录 role、status、voice、translator、notes 与 source revision；
- 英文 source 变更后中文 stamp 必须变 stale，重新审阅后才能盖章；
- 术语表固定同一城市、商品、官职、信仰和占法的主译名；别名只在首次出现时说明；
- UI 短文本若不属于 story 单元，可直接进入 i18n 源生成流程，但仍需中英同批。

### 10.7 文本验收

- 每个可用选择至少一个 applied effect 或一个 `queue_event`。
- 长后果链节点首句能反查上个选择。
- 正文声称的物品、城市、道路、钱、天数与 effects 逐项一致。
- 所有锁定选项都有玩家可理解的原因文本。
- source 内容有书目引用；authored 内容不冒充史料。
- `story.mjs check` 必须为 0 stale、0 missing；验证器不得存在 raw key 错误。
- 1280×720、200% 字号、英文最长文本三种条件下完整走读，不出现按钮含义被截断。
- 同一事件重新读档后随机结果文本与实际结算一致。

## 11. 美术需求

### 11.1 总体视觉

关键词：中世纪旅行手稿、羊皮纸舆图、波特兰航海图、墨线、矿物颜料、低饱和金色。
人物和城市允许地域差异，但统一纸张颗粒、线条粗细、光照方向和色阶。

禁止：

- 现代摄影、电影级写实 UI、霓虹、塑料高光；
- 把不同文化简单换色或混用标志建筑；
- AI 生成图中出现不可控文字、现代旗帜、错误宗教符号；
- 把透明棋盘格烘焙进像素。

### 11.2 技术规格

| 类别 | 尺寸 | 格式 | Alpha | 构图 |
|---|---:|---|---|---|

| 人物/导师立绘 | 768×1280 | WebP | 是 | 全身或 3/4 身，脚底完整 |
| 人物抽取卡底 | 1024×1536 | WebP | 否 | 上 20% 标题、下 25% 数据 |
| 城市地图小像 | 256×256 | WebP | 是 | 32 px 下仍可辨识 |
| 交通工具 | 512×256 | WebP | 是 | 左右朝向可翻转 |
| 道路笔刷 | 512×64 | WebP | 是 | 横向无缝拉伸 |
| 物品/线索 | 512×512 | WebP | 是 | 单物件，轮廓清晰 |
| 占卜工具 | 512–1024 方形 | WebP | 是 | 可拆分可交互部件 |

导入后正式版再转 KTX2/Basis；源文件保留无损母版。

构图安全区：

- 1280×720 裁切后仍保留主要地标，四边各留 5% 出血；
- 事件背景右侧或中央预留至少 42% 低细节区给正文面板，具体由 UI 布局模板标注；
- 关键人物面部不得落在标题、字幕、刘海屏安全区；
- 纯背景不烘焙文字、按钮和语言相关装饰；
- 小像与图标先在 32 px、64 px 灰度轮廓下验收，再看大图细节。

色彩与材质基线：

- 羊皮纸底色建议亮度 75%–90%，墨线与正文对比至少 4.5:1；
- 交互金色、锁定灰色、危险赭红必须同时辅以形状或图标；
- 统一从左上方入光，金箔只用于焦点和完成状态，不覆盖大面积正文底；
- 每个文化圈建立 1 页 reference sheet：建筑、服饰、器物、纹样、禁用混搭和来源。

### 11.3 地图资产

必须有：

- `fatequest-worldmap` 海岸、河流、海域、山脉、城市坐标和路线矢量层；
- 羊皮纸无缝底纹、旧墨迷雾、海陆墨线、四类道路笔刷；
- metropolis/city/town/station × 文化圈的城市小像；
- 山脉侧视立面、罗盘玫瑰、风神头、海怪、边框与文明纹样；
- 情报 1/2/3 级与当前城市的清晰状态；
- 城市详情卡与道路列表的图标语言。

验收：

- 关闭所有装饰贴图，仍能从矢量层辨认大陆海岸与主要河流；
- 开 6 倍缩放城市点击命中与绘制位置一致；
- 已知两城、未知道路时两城之间不出现笔触；
- 色觉缺陷模式不只靠红/绿表示已知和未知。

### 11.4 人物抽取资产

- 3 个现有身份各 1 张卡面/代表物：旅行书、草原缰绳、印度洋账册。

### 11.11 运行时预算

- 960×540 背景单张建议不超过 350 KB，特殊复杂场景上限 600 KB；
- 768×1280 透明立绘建议不超过 500 KB；
- 512×512 图标建议不超过 120 KB，地图小像不超过 80 KB；
- 同一事件页常驻纹理目标低于 24 MB 解压后显存；
- 12 城垂直切片运行资产目标低于 500 MB；无损母版不得进入发行包；
- 纹理超预算时优先调整尺寸、分层和压缩，不以损坏文本可读性换包体。

## 13. QA 与发布门禁

### 13.1 自动化

- JSON 合法、id 唯一、引用存在；
- effects op 合法且有 reason；
- `queue_event` 目标存在并计为被引用；
- `queue_event` 目标有选择且不存在直接或间接循环；
- 24 divinations 各有一个合法 lesson；
- 世界状态新增字段必须通过存档往返；
- 未知道路在 Travel 核心不可用；
- 后果队列按 FIFO 顺序、可存档、可消费；
- 内核不读取系统时间、不用非确定随机、不依赖 Node；
- i18n 无 raw key、来源标记完整。

最低测试分层：

| 层级 | 覆盖 | 何时执行 |
|---|---|---|
| 内容门禁 | schema、引用、来源、lesson、i18n | 每次内容提交 |
| 核心单测 | RNG、conditions、effects、Travel、SaveGame、LessonEngine | 每次代码提交 |
| 流程烟测 | 启动、抽取、后果链、地图卡、确认、学习、旅途恢复 | 每次合并前 |
| 固定种子旅程 | 三身份经济与道路可达性 | 每日或发布候选 |
| 存档 fixture | v1/v2、坏档、备份、更高版本 | 修改状态或存档时 |
| 视觉回归 | 720p、1080p、200% 字号、中英 | 每个里程碑候选 |

### 13.2 人工验收脚本

1. 新游戏连续抽三次，确认第三次后重抽禁用。
2. 接受人物，核对角色卡起点、HUD 当前城和自动档 header 一致。
3. 打开地图，点击一个已知但无已知道路的城市，确认卡片明确写“尚未获知道路”。
4. 在刺桐分别走三条入口分支，确认后果页紧接出现，状态与日志吻合。
5. 得知道路后观察迷雾与笔触，再从上路面板看到该道路。
6. 选择一种方式，确认未按出发时钱、日期、位置不变。
7. 确认出发，核对费用、天数、动画、途中事件、抵达顺序。
8. 抵达后重启并读自动档；核对角色、地图、背包、声望、随从、图鉴和天数。
9. 分别写入五个手动槽并交叉读取。
10. 学习占法：失败一次、跳过一次、成功一次；前两次技能列表不变，成功后出现。

### 13.3 性能目标

- 1280×720 桌面基准下地图平移/缩放保持 60 FPS；
- worldmap 运行时矢量产物控制在 200 KB 以内；
- 地图重绘不解析 JSON，不重复投影全部点；
- 自动存档目标小于 100 ms，失败只提示，不阻断入城；
- 城市/占卜背景按需加载，正式移动端核心包不装全量母版。

性能测量须记录机器、构建类型、分辨率、地图缩放、存档大小和连续运行次数。单次最好值
不作为验收；以至少 30 次的中位数和 P95 判断自动存档与地图帧耗。

2026-08-07 本轮 headless 基准（MacBook Pro Apple M2 Pro，Godot 4.7.1，40 次代表
性全地图状态；GPU 帧耗另见 `benchmark_map_fps.gd` 窗口实测）：

| 项目 | 结果 | 门禁 |
|---|---:|---:|
| 快照序列化 P95 | 5.93 ms | < 100 ms |
| 磁盘安全写入 median / P95 | 24.30 / 33.47 ms | P95 < 100 ms |
| Travel availability | 6120 次 / 827.12 ms | 记录趋势 |
| vector_map 运行包 | 90,397 B | < 200,000 B |
| 地图缩放 P95（窗口 1280×720，30 次） | 0.03 ms | < 16.7 ms |
| 地图平移 P95（窗口 1280×720，30 次） | 0.02 ms | < 16.7 ms |
| 常驻地图帧 median（窗口 1280×720） | 6.89 ms（≈145 FPS） | ≥ 60 FPS |

2026-07-30 基线（serialize 0.97 / save 5.21–5.39 ms）因 2026-08-06 内容增长
（i18n 5118 条、16 非 MVP 占法 resultTexts、24 课）自然升高，门禁不变。
完整机器可读数据见 `docs/benchmarks.json`。

地图逐帧路线动画已把山脉投影、路线端点/笔刷、城市图标/尺寸移到 `setup()` 缓存。GPU
60 FPS 与最大字号视觉帧耗仍须在非 headless 发布构建按上述 30 次口径人工记录。

桌面工程提供 Linux、macOS、Windows 三套导出预设；Linux preset 的 PCK 资源导出已通过，
包内确认存在主场景与 `content/world/vector_map.json`，并排除 `worldmap` 母版、工具、
测试、文档、创作源、归档图和工作表。完整平台可执行文件仍需相应官方 export template、
签名/公证和目标系统实机验收。
