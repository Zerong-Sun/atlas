## 1. 当前结论

### 2026-10-20 开局身份称呼与沉浸感修订

- 用户确认采用旧需求中的“丹吉尔式旅人”，替换运行时生硬的“白图泰式旅人”。`battuta` 显示为“丹吉尔式旅人 / A Traveller from Tangier”；`polo` 对应“威尼斯商旅 / A Venetian Merchant”，替换“波罗式旅人”。
- 开局称呼以出身和经历建立想象空间，不直接把随机年龄、跨年代的候选命名为历史人物本人。书名、史料署名及真实 NPC 的既有姓名保留。
- 身份称呼、背景和此行心愿分开表达。人物卡增加一段第二人称开篇，写眼前处境、随身物件和出发缘由，让玩家知道自己是谁、为何站在这座城。
- 其他角色保留已经写定的身份名；不从宗教、职业或画像反推个人姓名。
- 人物卡背景是游戏新撰叙事，不充作原书引文或严格历史年表。称呼修改不改变角色 ID、旧存档或人物图绑定。
- 验收：中英文均显示选定称呼和开篇；大字与小窗口可读，确认按钮可滚动到达；抽卡、重绘、确认及续玩不得退回“白图泰式旅人”“波罗式旅人”。

## 5. 多轮互动文本规格

### 5.0 可学习的细节与自然带出

结果正文只写玩家经历到的场景、人物反应和有趣细节，不复述系统已经完成的记录、地图标记、物品入包、耗时或属性变化（例如“见闻记进笔记”“路线已标在地图上”“货物收入行囊”“这趟花了 1 天”）。这类状态由界面标签或弹窗呈现；正文保留玩家为什么得到它、过程中看见或听见了什么。

### 5.0.1 对话视角与收尾

- **先说人话**：选项要能被玩家直接说出口。拒绝、改主意、暂缓时写“我现在不想去”“我还有别的安排”“等我想好了再说”，不要写“不把话带走”一类要读者猜意思的代称。
- **名词和后果落地**：账本写清记录了哪些货、货主、欠款或税额，以及丢失会怎样；“可怕”“太狠”“有用”“重要”等判断要换成符合当事人处境的准确词语和可见事实。
- **故事一旦开讲，就把故事讲出来**：不能用“说起金塔和河流”“介绍了做法”“讲了这座城的来历”概括玩家选择听到的内容。至少呈现起因、具体事件和一个可追问或被纠正的细节。
- **核对句间因果**：遗物的来源、人物是否亲眼见过、传闻是谁说的、哪件物证能证明什么，都要前后接得上；不以“他这么说，我就信”掩盖矛盾。
- **结果必须对上选项和地点**：已经进城的玩家不会再问“去本城怎么走”；“歇脚”“穿城”结果不能只复述操作。让当场人物给出一条新情报、一个具体回应或下段行程的实用细节。
- 互动正文以玩家正在经历的场景为中心。人物有话对玩家说，就让人物直接开口；避免用“他把布翻给你看”“她告诉你”“你听他讲完”代替本来可以直接呈现的对话或动作。必要的动作、环境和旁人反应仍可写，不能把整段改成没有场景的问答记录。
- 不用全知旁白替玩家规定感受、总结人物关系，或把刚发生的交流再转述一遍。保留第二人称现场感，人物的说话方式应符合身份、性格和当下处境。
- 结果段落不追加“你记在心里”“这份见闻收入行囊”“你的行迹又添一笔”等无新剧情信息的句子，也不以“告别后继续上路，心里有数”作通用收尾。若玩家确实拿到物件、承诺、路线或情报，直接写清楚得到的内容、来源和用处；系统状态由界面显示。
- 修订后逐句通读，确认对话像真人会说、动作在游戏场景里可见、每句话都提供角色反应/知识/选择后果/氛围中的至少一项。删掉只解释“刚才发生了什么”或为结果补尾声的句子。

### 5.0.2 城市故事点与继续行路

- 每座可到达城市至少有一个可点开的故事点，并提供至少一个能改变玩家接下来信息或行动的选项；单次入城介绍不替代城市里的互动故事点。
- 问路或选择出发时说清目的地和方向。选项揭示路线后，玩家应能在路线界面找到对应道路；不要只说“前面有路”“继续向远方走”。
- 路线界面优先列出尚未到访的城市并标明“新城”，让玩家容易走出熟悉的邻城往返。季节关闭或交通条件不足时，直接显示恢复时间或缺少条件。
- 每座城市至少保留一条可发现的出城路线；任何封路、费用或条件都要有明确提示，不能让玩家误以为没有下一站。

凡是文本承诺“讲清来路、做法、保存方式、行路规矩或地方风俗”，正文必须给出玩家能复述或应用的细节，不能用“她讲清了”“当地人很会做”“此地以此闻名”代替内容。按题材选择至少两项写实信息：

- **来路**：原料从哪里来，经谁之手、沿什么路线到眼前的人或货摊；标清亲历、转述和传闻。
- **步骤**：先后次序、工具或材料、火候/时间/季节，以及成败的可观察信号。
- **用途与保存**：物品如何使用、适合什么场景、如何包装或保存；区分容易混淆的品类，不把现代概念倒套给古人。
- **互动**：让角色通过示范、挑货、讨价、纠错或玩家追问自然说出知识，并给玩家一个能采取的下一步。

历史工艺和风俗细节需先核对一手史料或可靠学术/博物馆资料；证据不足就缩小断言范围或明确归为传闻，不为“有趣”补造配方、数字和普遍习惯。新增对白注明是依据来源的情境化改写时，不得伪装成原文引语。检查时问：玩家读完能否说出至少一个步骤、一个判断依据，以及它在这段互动中有什么用？

用户明确要求虚构奇闻的创作批次属于例外：可以原创神怪、夸张传闻、街头骗术和旅人吹牛，不要求这些故事有史实证据；但要让场景中的说话者和语气能辨认出这是故事、谣言、促销话术或故意编造，不得把新编内容登记为真实地方民俗或史料。不要拿现实群体的宗教仪式、圣迹或仍在传承的信仰当笑料；故事可以荒诞，角色的反应应自然、尊重且有辨别空间。

### 正向叙事、原创歌谣与解释

- 叙述先写人正在做什么、在意什么、如何与玩家来往；少用先防御、先否认、再改口的句式。
- 降低“不是 A 而是 B”、二分判断、连续排比和整齐的三段式比喻。段落长短和句子节奏随角色变化，避免每段都用“你问—他笑—他解释”的同一模板。
- 歌谣、童谣、号子和短诗可在用户授权的创作批次中原创。歌词应有具体场景、物件或动作，读起来像有人真会唱；由角色顺势解释意象、用途或歌里记下的知识。不要把新写歌词标成历史歌谣，也不要移植仍在传承群体的专属仪式文本。
- 解释应给玩家一层可理解、可复述的意义，例如歌谣怎样记住装船顺序、水路方向、织造步骤或邻里生活；保留故事感，不写成创作说明或百科脚注。

### 5.1 最低事件结构

每个需要多轮互动的对象至少由以下事件组成：

```text
第一轮事件
  ├─ 选择 A → 即时结果，或 queue_event → 第二轮事件
  ├─ 选择 B → 即时结果，或 queue_event → 第二轮事件
  └─ 选择 C → 轻量结果 + 下一步行动锚点

第二轮事件
  ├─ 选择 A → 物品 / 情报 / 关系后果
  ├─ 选择 B → 故事 / 图鉴 / 路线后果
  └─ 选择 C → 时间 / 风险 / 返回城市
```

重要故事可以继续到第三、第四页，但不得为了凑页数制造无意义的重复问答。

### 5.2 第一轮文本包

每个事件必须有：

| 文本 | 要求 |
|---|---|
| `title` | 点名地点、人物或事件，不用通用“城市探索” |
| `body` | 150–400 字英文源文；中文按语体等价翻译，不机械逐字对应 |
| 选择标签 | 3 个主要选择，动作明确，能看出差异 |
| 选择前置 | 钱、语言、占法、关系等限制必须写清原因 |
| `resultText` | 立即结算的选择必须说明变化和下一步 |
| `queue_event` | 需要继续剧情的选择必须指向有效事件 ID |
| `lore` | 标明 `source` / `authored` / `hybrid`，有来源时保留 ref |

### 5.3 后续事件文本包

后续事件不能只是重复第一轮正文。必须至少新增一种信息：

- 新人物发言或立场；
- 新的路线、城市、货物或风险信息；
- 新的物品交换、赠与、购买或损失；
- 新的图鉴/故事片段；
- 新的关系、声望或身份后果；
- 明确的行动锚点，例如“前往某城”“等待一天”“去找某人”。

### 5.4 结果文本和效果对齐

| 效果 | 文本必须说明 |
|---|---|
| `goods` | 物品名称、数量、获得/消耗原因、后续用途或限制 |
| `reveal_map` | 被揭示的城市或路线名称，以及为什么知道它 |
| `codex` | 获得的故事/知识主题，不能只说“图鉴更新” —— ✅ 2026-08-11 起正文与授予事件逐一对应，缺失即 G17 报错 |
| `sticker` | 贴纸代表的事件或纪念意义 —— ✅ 2026-08-11 起全部 60 张贴纸有正文，缺失即 G17 报错 |
| `reputation` | 哪一方对玩家的态度变化 |
| `days` | 等待或赶路的叙事原因和代价 |
| `coins` | 付款/报酬对象和交易原因 |
| `language` / `learn_divination` | 学习场景、用途和失败后果 |

每个效果至少满足一项：可见结果文本、后续事件、明确行动锚点。重要效果应同时满足两项以上。

## 6. 物品、故事、情报三类生产要求

### 6.1 物品型互动

物品不是单独显示一个名称就算完成。文本包必须包含：

1. 物品从谁处获得或购买；
2. 物品为何与当地场景有关；
3. 物品数量、价格或消耗条件；
4. 获得后的实际用途、货格影响或后续交易价值；
5. 中英文物品名、描述和结果反馈。

### 6.2 故事型互动

故事型互动必须产生可阅读内容：

1. 至少一段新正文，不得只复用城市简介；
2. 至少一个人物、地点或事件细节；
3. 选择后说明玩家带走了什么故事；
4. 如写入 codex，codex 正文必须与选择结果一致；
5. 对来源、改写和虚构部分标注 `lore.origin`。

### 6.3 情报型互动

情报必须能改变玩家下一步决策：

1. 点名城市、路线、关卡、水源、季节、语言或风险；
2. 明确情报从何而来；
3. 若揭示地图，`reveal_map` 的值必须和文本名称一致；
4. 给出行动锚点，例如去哪里、何时出发或需要准备什么；
5. 中英文不得出现不同地名、方向或数字。

## 7. 文本 authoring 与接线规范

新撰叙事文本的 authoring 源文件（运行词典另有 1601 个非 story 键，须按审计清单定位其生成器/历史维护源，不能宣称全词典都由此目录生成）：

```text
content/story/<unit>/en.md  ← 英文源文
content/story/<unit>/zh.md  ← 中文译文与校订
content/i18n/{en,zh}.json   ← story.mjs 编译产物，不直接手改
```

事件数据继续放在 `content/tables/events/`，不得在 UI 中硬编码剧情分支。每个新增后续事件必须：

- 使用稳定、可读、唯一的事件 ID；
- 由选择的 `queue_event` 接入；
- 在同一城市或有效范围内可触发；
- 所有选择带 `resultText` 或 `queue_event`；
- 所有 `effects` 带 `reason`；
- 中英文 key 同步存在；
- 重新运行生成器后仍可复现。

标准流程：

```bash
node tools/lore/story.mjs check
node tools/lore/story.mjs build
node tools/lore/story.mjs stamp zh  # 仅在逐条校译且记录完成后；批量工具会给所有单元盖章，勿用其消除待审状态
node tools/lore/story.mjs check
node tools/validate/validate.mjs --quiet
```

## 11. 中文玩家向叙事重写基准（2026-10-25）

用户反馈现有中文叙事过于文言、难读，排版不利于游玩；同时希望 NPC 迎接和城市探索呈现更多人物互动、角色性格与玩家选择。先以亚历山大、开罗、耶路撒冷、大马士革、刺桐五城试写，用户确认自然对白的方向后，本轮据此扩展并写入运行文本与事件数据。评审稿见 [`CHINESE_NARRATIVE_PILOT_REVIEW.md`](CHINESE_NARRATIVE_PILOT_REVIEW.md)，全城图像清单见 [`CHINESE_NARRATIVE_ART_PRODUCTION.md`](CHINESE_NARRATIVE_ART_PRODUCTION.md)。

本轮已按此基准完成 103 城及相关共享叙事中文重写；五城评审稿继续作为口吻示例和用户确认记录。写作基准与产物清单如下：

- 中文使用自然、简洁的现代白话；准确保留史实专名，避免行纪仿古句式和百科式信息堆叠；正文分段，人物换人换段。对白必须像当面交谈：先回应玩家真正问的事，再补有用信息；不把设计意图讲给玩家听，不用客套空话拖长一轮。
- 自然度负例：“别把‘指路’当成‘答应留宿’。主人家有自己的规矩。”（角色在解释作者的设计逻辑）；“他告诉你附近哪条巷子有常接待旅人的人家，再让开道路。”（同义重复，像动作说明书）。建议：“行，你去巷口那家问问。不过我可没说人家一定会收留你啊。”先把路指清楚，再用一句有性格的话提醒玩家，后续写到关键动作即可。
- 不为显得有趣而给每句加俏皮话；语气要符合人物、关系和处境。删掉不改变信息、人物、气氛或选择的句子。避免“你须知道”“凡……皆……”“就此展开在舆图上”等译腔模板。
- 风土细节从当下事情里自然出现：商人称货时顺口夸自己的织物，船员因风向改口谈季风，主人给客人递水时提本地待客习惯。允许人物自豪、卖弄、夸口或开玩笑，但要由他的身份、目的和对话触发；不让 NPC 停下来给玩家做地区说明，也不把一段正文塞成百科条目。
- 史料范围不止四本核心游记；地理学、宇宙志、王朝史和使节记录可用于人物的知识边界、路途闲谈和奇闻来源。新增史料及使用边界见 [`NARRATIVE_SOURCE_EXPANSION.md`](NARRATIVE_SOURCE_EXPANSION.md)，具体句子仍须按 `lore.origin/ref` 绑定证据，区分亲历、转述、学者知识和传闻。
- 每位重要 NPC 记录身份、目标、顾虑、性格、说话节奏、阅读/知识兴趣与初始态度；其见闻应匹配职业和受教育程度。对白体现人物性格，跨分支保持记忆与关系一致。
- 入城先呈现场景动作，再由 NPC 提出具体问题或行动，给出可辨认的玩家态度选项；选项后反馈必须与实际效果、线索或后续事件一致。
- 入城迎接按一个连续场景组织；多人可在同一场景轮流说话，玩家选择后留在当前对话继续，避免同一迎接过程连续弹出多个独立窗口。确需切场时要有明确的动作/地点承接，且对话可读完、暂停或退出。
- 每个场景和人物绑定独立插图需求。制作前先查 `portrait_art_map.json` 与图库盘点；确认缺图后再生成，不以通用异地素材顶替。人物图一人一图一 ID，场景背景与事件一一对应，并为对话 UI 留出安全区。
- 写完后逐条朗读所有可达分支，复核可读性、角色声线、分支衔接及选择结果；历史细节、物品和路线提示须对照来源及系统数据。

每批交稿做一次“正常人会这么说吗”朗读复核：如果一句话是在解释写作安排、重复玩家已经知道的事、或把一个简单请求绕成道理，就改成角色当场会说的短句。具体语气以用户提供的亚历山大城门对白范例及评审稿修订为基准。


## 12. 全城中文重写与世界观补充（2026-10-25）

本轮已从五城样稿扩展为 103 城与相关共享叙事文本的中文自然化生产；以玩家阅读顺畅、人物交流可信、选择有回应为目标。五城评审稿保留为示例和用户已确认的口吻基准，不再表示“仅交样稿、等待扩写”。城市级产物与图像缺口记录见 [`CHINESE_NARRATIVE_ART_PRODUCTION.md`](CHINESE_NARRATIVE_ART_PRODUCTION.md)。

- 只生产中文叙事；保留英文原文、英文 key、事件 ID、数值效果、存档字段和史料归属。不得把既有译本风格误当成必须保留的仿古语气。
- 对话先回答玩家当下问的事。问路就直接指路；顺带的提醒要像说话人的性格自然带出。删去对玩家解释剧情结构、重复动作和没有人物作用的客套句。
- 各地风俗、地理和物产由角色的职业、眼前动作、交易、赶路、待客或争论带出。人物可以自豪、卖弄或讲错，但要有说话动机；夸谈和传闻需让玩家听出来源，不让 NPC 忽然成为百科讲解员。
- 除四本核心旅行记录外，可参考当时及稍早的地理书、宇宙志、宫廷史、使节行记和抄本图像；这些材料代表不同年代和受教育者视角，不可自动套到普通居民身上。已核对的参考与使用边界见 [`NARRATIVE_SOURCE_EXPANSION.md`](NARRATIVE_SOURCE_EXPANSION.md)。新添具体历史断言须有来源锚点；创作补写须标 authored/hybrid。
- 多人迎接优先组织成一个连续场景内的轮流对话和玩家回应；不把一次见面拆成数个无动作承接的弹窗。
- “已重写”不等于“已获用户逐条审校”。本轮不新增 `reviewed` 或 `proofed` 声明；编译、key 对齐和机制保持检查只证明结构有效，不替代人工最终读稿。

## 13. 剧情与探索再次重写（2026-10-30，覆盖 §12 的交稿范围）

用户对上一轮的中文叙事仍不满意，要求重写全部剧情与探索，并增加文本量、对话长度和城市内可探索内容。当前批次包括入城、城市地点、道路事件、后续剧情、角色开场与结局；占卜课程、图鉴和界面提示暂不纳入。此轮允许同步改英文源文，以保持双语情节一致。

- 把解释作者意图或机制边界的句子改成场景中人物会做的事、会说的话。少用二分叙事、排比、对比句和警句；专业术语可以用，生造词和行业黑话不进玩家文案。
- 每一处对话都要有具体人物、眼前的事和选择后的变化。人物说话有来由，先回答玩家问的事；不同场景不反复套用“帮忙得声望／问路得路线”的同一种结构。
- 主要地点的正文须容纳真实的来回交谈：通常有两三轮问答，人物一边处理手头的事一边说话。约百余字、只有一句引语的段落需返工；扩写靠新的动作、误会、回应或关系变化，不靠重复说明。
- 以口述感、生活细节和人物关系增加故事活力；不模仿任何在世作家的特定措辞。用户明确否决“人物还没站稳”“秤可以等人，账可不能认错主人”“卖水的人嘴碎，路倒认得准”等不自然句子。卖水人相关对白可按用户示例使用：“那个卖水的人，超级嘴碎，不过嘛，问路的时候不会骗你哒。”
- 事件选择文本必须与天数、道具、声望、路线和后续事件的实际效果对齐。史料所述地点、年代与游戏的触发条件要相容；远方旧事写清是书中记载或别人转述，创作段落标 `authored` 或 `hybrid`。
- 事件表的 `coins` 数值以分计，100 分等于界面上的 1 银。写明金额时须按银换算；小额车费、船费可直接写用途，让界面显示准确数值。`days` 的正数会让日期前进，不能用负数表示“省时间”。
- 新增城内故事须接进城市 `sites`；每批按单元定向盖章并做文本与事件效果核查。按用户本轮分工，最终 i18n 构建、内容校验及 Godot 运行检查由用户统一执行。进度和未完成范围见 [`NARRATIVE_REWRITE_PROGRESS_2026-10-30.md`](NARRATIVE_REWRITE_PROGRESS_2026-10-30.md)。
